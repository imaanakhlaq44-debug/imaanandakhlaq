# Organisation Portals — Implementation Plan

An organisation — Alkhidmat, a telecom's CSR arm, a trust running forty
madaris — gets one link of its own. Its schools arrive through that link,
register themselves, and each one walks away with its own dashboard and its
own link for children. A child opens the school's link, types a roll number
and a PIN, and lands in their dashboard to submit work. No child has an email
address, a phone, or a password anywhere in this.

Extends `SCHOOL_GROUP_PLAN.md`, which made the school a group and gave it a
wall, and `PAPER_WORKFLOW_PLAN.md`, which let a school record work for
children who have no login. This plan is the layer above both: who hands the
school its link in the first place, and how a child reaches the app without an
account.

Decisions below are settled unless marked **OPEN**.

---

## 1. The three decisions everything else follows from

### 1.1 The organisation is a container, not a tenant

`orgs/{orgId}` holds a name, a slug and a join token. It does not hold
students, posts, consent, or any of the things a school holds. `schools` gains
one field — `org_id` — and every rule that already proves "same school" keeps
working untouched.

The alternative, a real tenant boundary, means every existing rule grows a
second question ("same org?") beside the one it already asks, and the two are
then free to disagree. `sameSchool(data)` is the only membership answer in
this app and it stays that way. An organisation is a way schools *arrive*, not
a wall between them.

A school with no `org_id` is a school that registered directly, exactly as
today. Nothing about the existing schools changes, and nothing needs
backfilling.

### 1.2 A child's session is a real Firebase session

The child signs in with a roll number and a PIN, and what comes back is a
**custom token minted for the student's own uid**. From that moment the child
is `request.auth.uid` like anybody else, and every rule in `firestore.rules`
already written for a student applies with no change.

This is the whole reason not to invent a parallel session. A PIN-only side
channel would mean a second definition of "who is this", one the rules engine
cannot see — so every student read and write would have to move behind a
callable, and the rules would quietly become decoration. Minting a token keeps
one answer to "who is this" in the system.

Firebase mints a custom token for a uid whether or not an Auth user record
exists, which is what makes this work for the `roster_only: true` children
`createRosterStudents` already creates. They stay loginless in the sense that
matters — no email, no password, nothing to remember but a slip of paper.

### 1.3 The link is readable, the secret is in the fragment

`/s/alkhidmat/gulshan-campus#7fK3aQ`

The path says whose link it is, because these get forwarded on WhatsApp and
printed on a notice board, and a link nobody can identify is a link nobody
trusts. The secret is the fragment, and the fragment is the point: a browser
never sends it to the server, so it stays out of access logs, out of `Referer`
headers, and out of any static host's records. `issueParentLink` already
issues `/wall/p#<token>` for exactly this reason, and this is the same
mechanism, not a new one.

The name is a **query**, not a path segment, and that is not cosmetic. This
site is a static SSG build with no rewrite rules — `.htaccess` has none and
there is no `_redirects` file — so `/s/alkhidmat/gulshan-campus` would need a
file per school, generated by a build that ran before the school existed.
`/s?org=…&school=…` is one real file answering for every school, with the
names still where a human can read them. `ParentWall` met the same wall and
answered it the same way, at `/wall/p#<token>`.

Only the fragment is load-bearing: `studentSignIn` resolves the school from
the token alone. The two slugs are there so a link forwarded on WhatsApp can
be recognised by whoever receives it.

## 2. Data model

```
orgs/{orgId}
  name              'Alkhidmat Foundation'
  slug              'alkhidmat'          unique, lowercase, url-safe
  join_token        secret in the org link's fragment
  contact_email, contact_phone
  status            'active' | 'closed'
  school_count      denormalised, for the org dashboard
  created_at, created_by

schools/{schoolId}
  org_id            (NEW, optional)      absent = registered directly
  slug              (NEW)                unique WITHIN the org
  … every existing field unchanged

school_links/{token}                                ← closed to every client
  school_id, org_slug, school_slug, created_at

users/{studentId}   role: 'student'
  roll_no           (NEW)  unique within the school, e.g. '31'
  pin_hash          (NEW)  scrypt, never the PIN itself
  pin_salt          (NEW)
  pin_set_at        (NEW)
  … every existing field unchanged

pin_attempts/{schoolId}_{rollNo}                    ← closed to every client
  fails             consecutive wrong PINs
  locked_until      ISO timestamp, absent when not locked
  last_attempt_at
```

Note what is **not** here: no `org_admins` collection, no per-org roles. An
organisation's own dashboard is a read of `schools where org_id == …`, and the
person who opens it is a `super_admin`. Giving organisations their own admin
accounts is a real feature with its own login, invitations and recovery — it
is **OPEN**, and deliberately out of this plan.

## 3. How a school arrives

1. Super admin creates the organisation and gets back
   `/join?org=alkhidmat#<join_token>` — one link, handed over once.
2. A school opens it. The page shows the organisation's name, so whoever
   opens it can see they are in the right place, and asks for the school's
   name, its head's email, and a password.
3. `registerSchoolInOrg` validates the join token, creates the `schools` doc
   with `org_id` and a slug derived from the name, creates the school admin's
   account, and returns the school's own student link.
4. **The school is live immediately.** No approval step.

That last point is a decision with a cost, and it belongs in writing rather
than in a later surprise: the join token is the only thing standing between
the link and a stranger's school. If it leaks, anyone who opens it can create
a school under that organisation's name. Three things keep that from becoming
a problem, and they are part of this plan, not an afterthought:

- **The token is revocable and rotatable.** One field on the org doc. Rotating
  it invalidates every copy of the old link at once; the schools already
  registered are unaffected, because they never use the join token again.
- **A new school starts empty.** It has no students, no wall, no consent
  records, and it cannot see any other school's anything — §1.1 guarantees
  that. The damage a fake school can do is to exist in a list.
- **The org dashboard lists every school with its registration date**, so a
  row nobody recognises is visible rather than buried.

**OPEN:** whether to cap registrations per token per day. Cheap to add, and
the only real defence if a token ends up in a WhatsApp group of 400 people.

## 4. How a child gets in

The school's dashboard gains a **Students** action that issues, for each
child, a roll number and a four-digit PIN. The PIN is shown **once**, at
issue, and printed on a slip — the same shape as `createTeacherAccount`, which
returns a password once and stores only what Auth keeps. Only `pin_hash` and
`pin_salt` are stored, using Node's built-in `scrypt`; no new dependency, and
no PIN recoverable from a database dump.

The child opens `/s/alkhidmat/gulshan-campus#7fK3aQ` and sees two boxes: roll
number, and PIN. No list of names.

That is why roll number and not a name picker. A name picker is easier for a
six-year-old, but the page is reachable by anyone holding the link, and a name
picker turns that link into a printed roster of every child in the school —
their names, their classes, on a page with no login in front of it. The roll
number keeps the roster inside the school, where it already lives.

`studentSignIn(school_token, roll_no, pin)` runs on the Admin SDK and:

1. Resolves `school_token` to a school. Wrong token, no school: the same error
   as a wrong PIN, so the response never confirms a school exists.
2. Reads `pin_attempts/{schoolId}_{rollNo}`. Locked, and it stops here.
3. Verifies the PIN with `scrypt` and a constant-time compare.
4. On failure: increments `fails`, and at **5** sets `locked_until` fifteen
   minutes out. Ten thousand PINs at five tries per fifteen minutes is eighty
   years per child, and that number is what makes four digits safe here.
5. On success: clears the counter and returns `createCustomToken(studentUid)`.

The lockout is per child, never per school — one child fumbling their PIN must
not lock a classroom out on activity day.

## 5. Routes

| Route | Who opens it | What it is |
|---|---|---|
| `/join?org=…` + `#join_token` | a school's head, once | register this school under the org |
| `/s?org=…&school=…` + `#student_token` | children, every week | roll number + PIN |
| `/orgs` | super admin | every org, its schools, and its links |

The first two are SSG pages that read their token from `location.hash` and
call a function; neither has anything a crawler can index, and neither takes a
secret through a path segment.

## 6. Rules

`orgs` is `allow read: if false` for every client. The registration page needs
the organisation's *name* before anyone has signed in, so the name comes back
from the callable that validates the token — not from a document the client
reads. A readable `orgs` collection would let anyone enumerate every
organisation in the system.

`pin_attempts` and `school_links` are `allow read, write: if false`, like
`parent_links`. Both are written only by the Admin SDK.

The school link is a separate collection rather than a field on the school,
and that is not tidiness. `schools` is `allow read: if signedIn()` — a token
stored there is a token every signed-in account in the system can read, which
is not a secret however carefully the fragment keeps it out of the logs. A
school reads its own link through `getSchoolLink`.

`schools` and `users` need no new clause at all. Both already gate updates
through `onlyKeys([…])` allowlists, so `org_id`, `roll_no`, `pin_hash` and
`pin_salt` are unwritable from a client the moment they exist — the existing
rule refuses every key it was not told about. That is the allowlist earning
its keep: a new field is closed by default rather than open by default.

## 7. Callables

| Function | Caller | Does |
|---|---|---|
| `createOrg` | super_admin | makes the org, returns the join link |
| `rotateOrgToken` | super_admin | new join token, old links die |
| `describeOrgInvite` | anyone with the token | returns just the org's name, for the register page |
| `registerSchoolInOrg` | anyone with the token | school + admin account + student link |
| `getSchoolLink` | school staff | the school's own link for children |
| `rotateSchoolLink` | school_admin | retire it and issue another |
| `listOrgs` | super_admin | every org and its join link, for the dashboard |
| `issueStudentPins` | school_admin, teacher | roll numbers and PINs for a class, shown once |
| `resetStudentPin` | school_admin, teacher | one child, one new PIN |
| `studentSignIn` | the child | §4 |

`describeOrgInvite` is deliberately thin. It answers one question — "what is
this organisation called" — and nothing else, because it is the one function
in this list that anybody on the internet can call.

---

## 8. Build order

Each step leaves the app working, and each one is testable before the next.

1. `orgs` collection, `createOrg`, `rotateOrgToken`, rules. Nothing user-facing
   yet; verified against the emulator.
2. `describeOrgInvite` + `registerSchoolInOrg` + the `/join` page. A school
   can now arrive.
3. `/orgs` dashboard for the super admin — the list, and the links.
4. PINs: `issueStudentPins`, `resetStudentPin`, the slip to print, and the
   Students panel that shows who has one.
5. `studentSignIn` + the `/s` page.

---

## 9. What this plan does not do

- **Org admin accounts.** §2. Organisations have no login of their own yet;
  the super admin runs their dashboard.
- **Moving a school between organisations.** Needs a story about what happens
  to the wall and to the parent links, and nobody has asked for it.
- **Per-org branding.** The register page shows the organisation's name. A
  logo is a `storage.rules` change and an upload flow, and it can wait.
- **The Android app.** Same as the wall: web only.
